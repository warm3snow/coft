# 密评 Skill 实施计划

## 1. 目标

基于已批准设计文档，落地一个面向“应用和数据安全”的密评 Skill。该 Skill 采用“LLM 直接读仓库 + 按规则判定”的方式，对目标代码仓库进行静态审计，重点覆盖：

- 数据加密
- 鉴权与访问控制
- 通信安全
- 国密适配线索

产物必须包含 Markdown 和 HTML 两种报告格式，并保留可追溯的文件证据。

## 2. 落地假设

- `agent-skills/` 当前基本为空，需要从零建立 Skill 目录、文档与最小可运行骨架。
- 仓库内已存在一个可参考的 LLM 工程样例：`ai-engineering/multi-agent-platform/`，其中的配置、LLM 调用、结构化输出和工具编排思路可复用，但不强耦合依赖其整个平台。
- 首版目标是可演示、可扩展的 Skill，而不是一次性做成完整密评产品。

## 3. 实施阶段

### Phase 1：Skill 骨架与配置打通

目标：先让 Skill 具备可执行入口、参数输入、LLM 配置和基础目录结构。

任务：

1. 在 `agent-skills/` 下建立密评 Skill 的目录结构。
2. 定义 Skill 入口文档，例如 `SKILL.md`、使用说明、输入参数说明。
3. 建立基础配置层：模型名称、API Key、Base URL、最大上下文大小、忽略目录、支持文件类型。
4. 明确运行方式：本地 CLI 驱动或通过现有 Agent 框架调用。

完成标准：

- Skill 可以接收仓库路径并完成一次空跑。
- 配置项可通过环境变量或配置文件控制。

### Phase 2：仓库读取与上下文构建

目标：让 Skill 能稳定读取目标仓库，并把代码内容整理成适合 LLM 判定的输入。

任务：

1. 实现文件发现器，识别源码、配置、依赖、部署文件。
2. 建立忽略规则，跳过 `.git`、缓存目录、二进制文件、大图片、大型依赖目录等低价值内容。
3. 实现分片策略：按目录、文件类型、文件大小或风险域拆分上下文。
4. 为每个上下文片段保留文件路径、片段行号范围和片段摘要。
5. 明确超长仓库的降级策略，例如分域扫描或分批多轮判定。

完成标准：

- Skill 能输出稳定的上下文片段列表。
- 每个片段都能回溯到原始文件。

### Phase 3：规则模板与 Prompt 体系

目标：把密评检查口径显式化，避免 LLM 自由发挥。

任务：

1. 为四个风险域定义规则模板和判定标准。
2. 设计统一 Prompt 模板，包含：角色、规则、禁止项、输出 schema、证据引用要求。
3. 定义风险等级与置信度口径。
4. 定义人工复核场景与触发条件。
5. 设计例外规则与误报抑制机制，至少支持配置式白名单。

完成标准：

- 每次 LLM 调用都基于固定模板。
- 提示词中明确要求引用仓库内文件证据。

### Phase 4：LLM 判定与结果校验

目标：完成从仓库上下文到结构化 Findings 的主链路。

任务：

1. 实现 LLM 调用器，支持重试、超时和错误回传。
2. 使用结构化输出约束 Findings schema。
3. 实现结果校验器，检查字段完整性、文件路径合法性、风险等级枚举、证据是否存在。
4. 对不合规输出执行修复重试；仍失败则降级为 `manual_review`。
5. 归并重复 Findings，避免同一问题被多片段重复报告。

完成标准：

- Skill 能从一个真实仓库生成结构化 Findings。
- 非法输出不会直接进入最终报告。

### Phase 5：报告渲染

目标：把 Findings 产出为可交付报告。

任务：

1. 渲染 Markdown 报告。
2. 渲染单文件 HTML 报告。
3. 统一摘要结构，包括：扫描目标、时间、问题总数、风险分布、人工复核项。
4. 在详细问题中展示文件路径、证据片段、规则依据、整改建议。
5. 为 HTML 加入最小交互能力，例如筛选、折叠和高亮。

完成标准：

- 同一次扫描输出 `.md` 和 `.html` 两种报告。
- Markdown 与 HTML 的信息结构一致。

### Phase 6：测试与样例仓库

目标：让首版 Skill 具备基本可信度和回归能力。

任务：

1. 构建最小样例仓库，覆盖明文密钥、弱算法、未启用 TLS、未鉴权接口等典型问题。
2. 编写单元测试，覆盖仓库分片、Prompt 构造、结果校验、报告渲染。
3. 建立 golden report 回归测试，固定输入仓库并校验输出结构。
4. 补充失败场景测试，例如超大文件、二进制文件、LLM 非结构化输出。

完成标准：

- 核心模块具备自动化测试。
- 典型输入的报告结构稳定。

## 4. 建议目录结构

```text
agent-skills/
  guomi-app-data-security/
    SKILL.md
    README.md
    requirements.txt
    src/
      guomi_skill/
        __init__.py
        config.py
        scanner.py
        context_builder.py
        prompting.py
        adjudicator.py
        validation.py
        reporting.py
        models.py
    tests/
      test_context_builder.py
      test_validation.py
      test_reporting.py
    fixtures/
      insecure-demo-repo/
```

这个结构把“读取仓库”“构建上下文”“调用 LLM”“校验结果”“渲染报告”分开，便于单测和后续增强。

## 5. 实施顺序建议

按以下顺序推进，避免先做重模块再返工：

1. Skill 目录与配置。
2. 仓库发现与上下文分片。
3. Findings 数据模型与输出 schema。
4. Prompt 模板与 LLM 调用器。
5. 结果校验与重复归并。
6. Markdown/HTML 报告。
7. 样例仓库与测试。

这个顺序的原因是：仓库读取、结构化输出和校验机制决定了后面所有模块的边界。如果这些边界不先定，Prompt、报告和测试都会反复改。

## 6. 风险与应对

- 风险：LLM 直接读仓库导致上下文过大。
  应对：分片扫描、分域提示、限制单次输入大小。

- 风险：模型输出不稳定。
  应对：固定 Prompt 模板、固定 schema、增加输出校验和修复重试。

- 风险：误报过多。
  应对：增加白名单抑制、引入 `manual_review` 状态、优先做高价值规则。

- 风险：HTML 报告过度复杂。
  应对：首版使用单文件静态模板，不引入前端构建链。

## 7. 第一轮实施范围

第一轮只做最小可用版本，严格控制范围：

- 支持本地目录扫描。
- 支持常见文本文件类型。
- 覆盖四大风险域的基础规则。
- 生成结构化 Findings。
- 输出 Markdown/HTML 报告。
- 提供最小样例仓库和基础测试。

以下能力明确延后：

- 深层 AST 分析。
- 自动修复建议代码生成。
- 多模型比较或投票。
- 远程仓库拉取与在线服务化部署。

## 8. 完成判据

当满足以下条件时，认为首版实现完成：

1. 用户可指定一个本地代码仓库运行 Skill。
2. Skill 能读取仓库并分批提交给 LLM。
3. Skill 能按固定 schema 输出 Findings。
4. Skill 能生成 Markdown 与 HTML 报告。
5. 核心模块有自动化测试，样例仓库可稳定复现预期结果。
