# Story-AC Author Skill 设计

> 生成日期: 2026-06-01
> 目标位置: `agent-skills/story-ac-author/`
> 状态: design (待评审)

## 1. 目的与范围

定义一个用于把"自然语言需求"转换为"敏捷 User Story + 可测试可验收的 Acceptance Criteria"的 skill。skill 在生成前与用户进行交互式澄清，覆盖 5 个固定维度；澄清完成后产出符合 Given-When-Then 规范并通过 4 项硬性检查的 AC。

skill 只定义标准与行为边界，不实现执行器、解析器或外部模型调用。skill 的产出是落盘到仓库的 Markdown 文档。

### 1.1 不在范围 (Out of Scope)

- 不做需求采集后的工作量估算、优先级排序、迭代规划
- 不做任务分解到工程子任务（实施级）
- 不实现可运行的脚本或工具链
- 不替代正式的需求评审流程

## 2. 设计要素汇总

| 维度 | 决策 |
| --- | --- |
| Story 格式 | 敏捷标准 (As a / I want / So that) |
| AC 格式 | Given-When-Then (BDD) |
| 澄清维度 | 固定 5 维：用户角色 / 核心场景 / 边界异常 / 验收判定 / 范围边界 |
| 提问方式 | 按需提问（识别已明确的维度后跳过），一次一题 |
| AC 测试性约束 | 4 项硬性检查（输入具体 / 期望可观察 / 边界明确 / 可独立验证） |
| 大需求处理 | 支持 Epic 拆分 → 多个 Story |
| 输出路径 | `docs/stories/YYYY-MM-DD-<slug>.md`，Epic 模式建子目录 |
| 输出格式 | 仅 Markdown |
| 文件骨架风格 | 与 `guomi-app-data-security`、`ai-codebase-docs` 完全对齐 |

## 4. 澄清阶段：5 维度规则与按需提问

### 4.1 五个澄清维度

| # | 维度 | 必须搞清的事 | "已明确"判定标准 |
|---|---|---|---|
| 1 | 用户角色 | 谁会用？是否多角色？权限差异？ | 用户原始描述里点名了具体角色（"注册用户"/"管理员"/"游客"），且角色单一或差异已说明 |
| 2 | 核心场景 | 触发条件、主流程步骤、价值结果 | 用户说清了"什么时候触发 → 走什么流程 → 拿到什么结果" |
| 3 | 边界与异常 | 输入边界、并发、超时、错误分支、空态 | 用户主动列出了至少 1 个失败/异常分支 |
| 4 | 验收判定 | 怎么算"做完了"？可观察的成功信号 | 用户给出可观察指标/结果（"返回 200" / "页面跳转到 X" / "数据库写入"） |
| 5 | 范围边界 (Out of Scope) | 这次不做什么？依赖谁？ | 用户主动声明了不做项或下游依赖 |

### 4.2 按需提问判定流程

```
对每个维度 i ∈ {1..5}:
  if 该维度已"明确"（按 4.1 表标准）:
     skip，在内部澄清记录中标注 "明确(原文证据: ...)"
  else:
     生成 1 个针对性问题（优先多选，否则开放式）
     一次只问 1 个问题，等待用户回答
     回答后重新判定该维度是否明确
循环直到 5 个维度全部"明确"
```

### 4.3 提问优先策略

- 优先**多选题**（A/B/C，覆盖常见取值）
- 实在无法穷举时用开放式问题
- 每题需附"为什么问"（一句话），让用户理解必要性

### 4.4 澄清阶段的硬约束（写入 HARD-GATE）

- 不得跳过 5 维度中任何一个维度
- 不得在同一条消息里问多个澄清问题
- 不得用"假设默认值"代替提问（除非 `standards.md` 中已明确允许）
- 不得把"用户未提及"等同于"无要求"

## 5. AC 4 项硬性检查与禁止写法

### 5.1 4 项硬性检查

每条 AC（Given-When-Then 三段）必须在落盘前满足全部 4 项：

| # | 检查项 | 通过标准 | 不通过示例 → 修正示例 |
|---|---|---|---|
| 1 | 输入具体 | Given/When 中所有"输入数据/前置状态"必须是具体值或具体集合，不得用模糊词 | "用户输入合适的密码" → "用户输入符合 8-20 位、含数字+字母的密码 'Abc12345'" |
| 2 | 期望可观察 | Then 中的"结果"必须是外部可观察的：UI 文案/路由跳转/HTTP 状态码/响应字段/数据库行变化/事件发出 | "系统正确处理请求" → "API 返回 200 + body 中 `data.userId` 为新创建用户 ID" |
| 3 | 边界明确 | 凡涉及范围/时间/并发/数量的 AC，必须标注边界值 | "验证码有效期内可用" → "验证码自下发起 5 分钟内有效，第 6 分钟必须返回 410 Gone" |
| 4 | 可独立验证 | 该 AC 不依赖其他 AC 的执行结果就能单独验证（每条 AC 自带必要前置） | "AC-2 在 AC-1 完成后..." → "AC-2: Given 用户已登录（前置可独立构造），..." |

第 4 项允许 AC 之间共享前置，但**前置必须独立可构造**——不能强依赖另一条 AC 的执行结果才能成立。

### 5.2 禁止写法

skill 必须拒绝产出含以下关键词的 AC：

| 禁止词 | 原因 | 修正方向 |
|---|---|---|
| "正确地" / "合适的" / "合理的" | 主观、不可验证 | 替换为具体阈值或可观察行为 |
| "尽快" / "及时" / "高效" | 无可测量边界 | 给出 SLA 数值（如 "P95 < 500ms"） |
| "易用" / "友好" / "美观" | 主观感受 | 用具体行为/UI 文案替代 |
| "支持" / "兼容" 后接模糊对象 | 范围不清 | 列出具体对象集合（"支持 Chrome 100+ / Firefox 100+"） |
| 仅描述实现而无外部观察 | 不可验收 | 改写为外部可观察的行为/数据 |

### 5.3 Story 自身的轻量检查

Story 主体（As a / I want / So that）也要满足：

- **角色具体**: 不得为泛化"用户"，必须是已澄清出的具体角色
- **价值清晰**: So that 子句必须能回答"为什么要做"，不得是 "so that the feature works"
- **不含实现细节**: I want 子句描述目标，不指定技术方案

### 5.4 输出前自检流程

skill 在落盘前对每条 AC 跑一遍 4 项检查，**任何一项失败都必须先修正再落盘**，并在生成的文档底部追加一段"AC 检查通过记录"作为验收凭证。

## 6. Epic 拆分判定与多文件输出

### 6.1 何时触发 Epic 拆分

skill 在完成 5 维度澄清后、生成 Story 前先评估，**满足以下任一条件即提示拆分**：

| 信号 | 触发条件 |
|---|---|
| 多个独立用户角色 | 澄清后发现 ≥ 2 个角色，且各角色有独立的核心场景 |
| 多个独立价值点 | "So that" 子句中能写出 ≥ 2 个互不依赖的收益陈述 |
| 多个独立流程入口 | 触发条件/入口超过 1 个，且各入口的成功路径不重叠 |
| AC 数量过载 | 预估 AC 数量 > 8 条（强信号：单 Story 过胖） |
| 跨多个数据/系统边界 | 涉及 ≥ 2 个独立子系统/服务/数据域 |

### 6.2 拆分判定流程

```
评估 5 个信号
  └─ 0 个命中 → 单 Story（走标准生成流程）
  └─ ≥ 1 个命中 → 进入 Epic 拆分:
       1) 向用户展示拆分建议（列出建议拆出的 Story 标题 + 拆分依据）
       2) 等用户确认/调整拆分
       3) 对每个 Story 走完整的 5 维度澄清（复用已澄清的公共维度）
       4) 逐个生成 Story + AC
```

### 6.3 拆分阶段的硬约束

- 不得不经用户确认就直接拆 Epic 或合并 Story
- 拆分后每个 Story 必须独立通过 5 维度澄清，不得共享含糊维度
- 公共上下文（角色定义、术语）可在 Epic 索引文件中沉淀，不在每个 Story 重复

### 6.4 文件落盘约定

#### 单 Story 模式

```
docs/stories/2026-06-01-sms-login.md
```

- slug 由用户确认后的 Story 主标题派生：转小写 → 空格与下划线转 hyphen → 去除停用词（中文如"的、了、在"；英文如 "the/a/an/of"）→ 仅保留 ASCII 字母数字与 hyphen → 连续 hyphen 合并 → 截断至 40 字符并去除首尾 hyphen
- 若 slug 派生后为空（如纯特殊符号标题），skill 必须停止落盘并请用户提供英文/拼音 slug
- 日期取生成当日

#### Epic 模式

```
docs/stories/2026-06-01-user-auth/
├── README.md                      # Epic 索引
├── 01-sms-login.md
├── 02-password-reset.md
└── 03-account-lockout.md
```

- Epic 单独建子目录，目录名同样为日期 + slug
- 子 Story 文件名前缀 `NN-` 表示建议交付顺序（不强制依赖）
- Epic `README.md` 列出共享角色定义、术语表、Story 列表与依赖关系（用 `depends_on` 字段显式声明）

### 6.5 命名冲突处理

- 同日同 slug 已存在 → 追加后缀 `-v2`、`-v3`
- 不得覆盖已有文件，不得静默重命名

### 6.6 落盘前的最终检查

skill 在写文件前必须确认：

- [ ] 5 维度全部明确
- [ ] 每条 AC 通过 4 项硬性检查
- [ ] Epic 拆分（如适用）已用户确认
- [ ] 文件路径不与已有文件冲突
- [ ] Epic 索引中 `depends_on` 引用的 Story 文件全部已生成

任一项未通过，**不得落盘**。

## 7. 输出模板

### 7.1 单 Story 文件模板

```markdown
# Story: <一句话标题>

> 生成时间: 2026-06-01
> 角色: <已澄清的具体角色>
> 状态: draft

## Story

As a <具体角色>
I want <目标，不含实现细节>
So that <可识别的业务价值>

## 上下文 (Context)

<2-4 句澄清后的关键背景：触发场景、上游/下游关系、为什么现在要做>

## 范围 (In Scope)

- <本 Story 包含的能力点 1>
- <本 Story 包含的能力点 2>

## 不在范围 (Out of Scope)

- <明确不做的项 1，附简短理由>
- <明确不做的项 2>

## Acceptance Criteria

### AC-1: <一句话场景标题>
- **Given** <具体的前置状态/数据>
- **When** <用户/系统的具体动作>
- **Then** <可观察的结果，含具体值>
- **And** <附加可观察结果（可选）>

**边界**: <若涉及范围/时间/并发/数量，明确边界值>
**验证方式建议**: <单测 / 接口测试 / E2E / 手工 中的一项或多项>

### AC-2: ...

## 依赖与假设

- 依赖: <上游服务/数据/前置 Story，无则写"无">
- 假设: <skill 已与用户确认的隐性前提>

## 澄清记录

| 维度 | 状态 | 依据 |
|---|---|---|
| 用户角色 | 明确 | 用户原文："注册用户" |
| 核心场景 | 明确 (轮 1 提问) | 用户回答：A |
| 边界与异常 | 明确 (轮 2 提问) | 用户回答：5 分钟超时 |
| 验收判定 | 明确 (轮 3 提问) | 用户回答：返回 200 + token |
| 范围边界 | 明确 | 用户原文："不做第三方登录" |

## AC 检查通过记录

| AC | 输入具体 | 期望可观察 | 边界明确 | 可独立验证 |
|---|---|---|---|---|
| AC-1 | ✓ | ✓ | ✓ | ✓ |
| AC-2 | ✓ | ✓ | ✓ | ✓ |
```

```markdown
# Epic: <一句话标题>

> 生成时间: 2026-06-01
> 状态: draft

## 背景

<3-5 句：业务目标、用户问题、为什么需要拆成多个 Story>

## 共享角色定义

| 角色 | 定义 |
|---|---|
| 注册用户 | 已通过手机号注册并完成实名认证的自然人用户 |
| 管理员 | 拥有后台账户管理权限的运营人员 |

## 术语表

| 术语 | 定义 |
|---|---|
| 验证码 | 6 位数字，5 分钟有效期，单次使用 |

## Story 列表

| 序号 | Story | 依赖 (depends_on) | 文件 |
|---|---|---|---|
| 01 | 验证码登录 | 无 | [01-sms-login.md](./01-sms-login.md) |
| 02 | 密码重置 | 01 | [02-password-reset.md](./02-password-reset.md) |
| 03 | 账号锁定 | 01 | [03-account-lockout.md](./03-account-lockout.md) |

## 拆分依据

- 多个独立价值点：登录 / 重置 / 防爆破，三者用户路径独立
```

### 7.3 模板使用约束（写入 HARD-GATE）

- 不得删除模板中的"澄清记录""AC 检查通过记录"两个表格——这两个表是验收凭证
- 不得用空表占位——表格存在但内容为空视为未通过 Output Gate
- 自定义新增章节允许，但不得删除已有的强制章节

## 8. SKILL.md 守门口

### 8.1 HARD-GATE（汇总）

```
<HARD-GATE>
在使用这个 Skill 时，必须遵守以下规则：

澄清阶段
- 不得跳过 5 维度中任何一个维度。
- 不得在同一条消息里问多个澄清问题。
- 不得用"假设默认值"代替提问。
- 不得把"用户未提及"等同于"无要求"。

Story 与 AC 生成
- 不得在 5 维度未全部明确前生成 Story。
- 不得产出含模糊词（"正确地"/"合适的"/"尽快"/"易用"等）的 AC。
- 不得产出 4 项硬性检查未全通过的 AC。
- 不得产出依赖另一条 AC 执行结果才能验证的 AC。
- Story 的 As a 子句不得使用泛化"用户"，必须为已澄清的具体角色。

Epic 拆分
- 不得不经用户确认就拆分或合并 Story。
- 拆分后每个 Story 必须独立通过 5 维度澄清。

落盘
- 不得覆盖已有文件，不得静默重命名。
- 不得删除模板中的"澄清记录"和"AC 检查通过记录"表格。
- 不得用空表占位。
- 任务要求生成文档时，必须实际创建文件，不得只在对话中给出文本。
</HARD-GATE>
```

### 8.2 Output Gate（落盘前自检）

```
在落盘 Story/Epic 文件前，逐项确认：

1. 5 维度澄清记录表是否每行都为"明确"，且都附依据？
2. 每条 AC 是否通过 4 项硬性检查（输入具体 / 期望可观察 / 边界明确 / 可独立验证）？
3. AC 中是否含禁止词（正确地/合适的/尽快/易用/友好/...）？
4. Story 的 As a / I want / So that 是否分别满足"角色具体 / 不含实现 / 价值清晰"？
5. Epic 模式下，索引文件的 Story 列表是否与已生成的子文件一一对应？
6. 文件路径是否与已有文件冲突？
7. 模板中的"澄清记录""AC 检查通过记录"两个表是否填充完整？

任一答案为"否"，不得落盘，回到上一步修正。
```

### 8.3 Required Order（必做顺序）

```
1. 先读 standards.md，理解 5 维度判定规则与 AC 4 项检查口径。
2. 再读 output-template.md，理解模板强制字段。
3. 输出风格不确定时，再看 examples.md。
4. 对用户输入做 5 维度评估，按需提问，一次一题。
5. 5 维度全部明确后，评估是否触发 Epic 拆分。
6. 若拆分，向用户确认拆分方案后，逐 Story 走完整流程。
7. 生成 Story + AC，对每条 AC 执行 4 项硬性检查并记录。
8. 走 Output Gate 自检；不通过则修正后重新过一次，循环直至全部 7 项通过。
9. 写入 docs/stories/，并在对话中告知文件路径。
```

### 8.4 Review Checklist（结束前确认）

```
- [ ] 5 维度澄清记录表完整。
- [ ] 每条 AC 都通过 4 项硬性检查。
- [ ] AC 中无禁止词。
- [ ] Story 的角色为具体角色而非"用户"。
- [ ] Epic 模式下索引文件已生成且依赖关系清晰。
- [ ] 文件已实际落盘（不是只在对话里展示）。
- [ ] 输出路径已告知用户。
```

### 8.5 Common Failures（红旗清单）

```
- 跳过澄清，直接根据用户原始输入猜测 Story。
- 用"系统正确处理"等模糊表达写 AC。
- AC 间形成串行依赖（AC-2 必须 AC-1 通过后才能验证）。
- Epic 未与用户确认就直接拆分。
- 在对话里输出 Story 文本但未实际写文件。
- 澄清记录表只勾选"明确"但不写依据。
```

## 9. examples.md 内容计划

`examples.md` 在实现阶段填充以下内容：

- **好例 1 个**: 单 Story 完整样例（包含完整澄清记录、4 项检查通过表）
- **坏例 1 个**: 故意展示 AC 中的禁止词、模糊期望、串行依赖等典型错误及修正
- **Epic 拆分对话片段 1 个**: 展示从识别拆分信号到与用户确认拆分方案的对话过程
- **典型按需提问对话 1 个**: 展示哪些维度被识别为"已明确"而跳过、哪些维度被提问
- **反模式 3-5 条**: 列举常见错误使用方式（如跳过澄清、用 HTML 输出、覆盖已有文件等）

## 10. README.md 内容计划

`README.md` 包含：

- 阅读顺序：`SKILL.md` → `standards.md` → `output-template.md` → `examples.md`
- 文件说明：每个文件的职责一句话描述
- 使用要点：先读 SKILL.md 硬约束、按需提问而非穷举、AC 落盘前必过 4 项检查
- 设计原则：skill 只定义标准、产出必须有澄清证据、AC 必须可独立验证

## 11. 与现有 skill 的关系

- 与 `guomi-app-data-security` 关系：互补。前者审阅"已写代码"的合规风险；本 skill 在"写代码之前"约束需求质量。两者不冲突，可串联使用。
- 与 `ai-codebase-docs` 关系：互补。前者沉淀"系统现状文档"；本 skill 沉淀"待开发需求文档"。落盘目录不同（`docs/ai/` vs `docs/stories/`）。

## 12. 设计原则

- **skill 只定义标准，不实现执行器**：与目录中其它 skill 一致
- **澄清证据先行**：所有 Story 必须附澄清记录表，不允许"凭感觉"产出
- **AC 必须可独立验证**：所有 AC 必须满足 4 项硬性检查，不可通过则不得落盘
- **拒绝模糊**：禁止词清单是硬性筛子，不允许例外
- **真实落盘**：要求生成文档时必须创建文件，不得只在对话中展示文本
