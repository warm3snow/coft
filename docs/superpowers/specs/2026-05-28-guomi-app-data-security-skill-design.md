# 密评 Skill 设计文档

## 1. 背景与目标

本设计面向 `agent-skills/` 新增一个聚焦“应用和数据安全”的密评 Skill。这个 Skill 的职责不是实现扫描器、调用外部模型或承载执行框架，而是定义一套供 LLM 遵循的密评标准、检查范围、输出要求与行为约束。

目标是让 Agent 在读取代码仓库内容后，严格按照 Skill 给出的评测标准识别并评估以下几类问题，并生成可交付的审计结论：

- 数据加密：敏感数据是否加密存储，是否存在明文密钥、弱算法或未加密落盘。
- 鉴权与访问控制：认证机制是否存在缺失、弱口令/硬编码凭据、越权风险、Token/Session 处理不当。
- 通信安全：传输层是否启用 TLS/HTTPS，是否存在明文协议、证书校验关闭、弱加密套件。
- 国密适配线索：是否使用 SM2/SM3/SM4、国密 TLS、国密证书链，或是否仍依赖非国密算法作为关键安全能力。

核心产出为两种格式：

- Markdown 报告：便于在仓库、PR、知识库中查看。
- HTML 报告：便于对外展示、归档与打印。

首版强调“标准清晰、边界清晰、判断口径清晰、输出要求清晰”，而不是实现扫描引擎或形式化认证结论。

## 2. 范围

### 2.1 In Scope

- 定义源码、配置文件、依赖清单、容器配置与常见部署描述文件的检查重点。
- 定义应用与数据安全问题的判定口径。
- 定义结构化问题清单、风险等级、证据位置、修复建议的输出要求。
- 规定 Markdown 与 HTML 两种报告格式要求。
- 明确区分“已确认问题”“高置信线索”“需要人工复核”。

### 2.2 Out of Scope

- 动态渗透测试、运行时抓包、主动探测、联机攻击验证。
- 合规认证自动出证或替代人工密评。
- 覆盖主机、网络边界、数据库实例、密码机等基础设施层面。
- 自动修改业务代码或自动修复漏洞。
- 在 Skill 内实现扫描器、解析器、报告渲染器或外部模型调用脚本。

## 3. 设计原则

- Skill 只定义标准，不实现执行：仓库读取、文件搜索、上下文拼接和模型调用由宿主 Agent 或运行环境负责，Skill 只约束“该看什么、怎么判断、怎么输出”。
- 规则显式化：每个安全域都要有可引用的检查规则、判定标准与输出模板，避免让模型自由发挥。
- 证据先于结论：每个结论都必须附带文件、位置、命中规则与判断依据。
- 保守输出：置信度不足时标记为“待人工确认”，避免伪确定性。
- 国密导向但不教条：既识别国密能力，也指出关键路径上不符合国密预期的传统算法使用。
- 行为受控：Skill 必须明确 LLM 应该做什么、不应该做什么，特别是不得虚构证据、不得推断未读文件、不得把最佳实践偏差直接认定为合规不通过。
- 可扩展：规则集、提示词模板、报告模板后续可独立扩展。

## 4. 候选方案与取舍

### 方案 A：Skill 内置执行逻辑

做法：在 Skill 中同时定义密评标准、扫描逻辑、上下文处理、LLM 调用与报告生成。

优点：表面上看一体化，交付物集中。

缺点：违背 Skill 的职责边界，把“标准”和“执行器”混在一起，后续维护和复用都很差。

### 方案 B：Skill 只定义密评标准与行为边界

做法：Skill 仅提供检查域、判断规则、输出格式、风险分级、禁止行为和人工复核准则；具体仓库读取与模型调用由宿主 Agent 按 Skill 执行。

优点：边界清晰、职责单一、便于复用，也最符合 Skill 的定位。

缺点：需要宿主 Agent 具备基本的仓库读取和执行能力，Skill 本身不直接产出结果。

### 方案 C：Skill + 独立工具链组合

做法：Skill 只定义标准，另有单独项目实现扫描器、证据提取器或报告工具，运行时由 Agent 同时调用两者。

优点：边界明确，后续可以独立演进工具链。

缺点：当前仓库里并没有这套独立工具链，若现在设计进去会把 Skill 文档复杂化。

推荐采用方案 B。当前 Skill 应当聚焦于“定义密评标准与 LLM 行为边界”，不在 Skill 内写扫描脚本、上下文构建器或外部模型调用逻辑。

## 5. Skill 结构

Skill 本身不承载执行流水线，而是由以下文档化模块组成：

1. `scope definition`：定义检查范围、覆盖对象与不覆盖对象。
2. `evaluation standard`：定义各风险域的判断规则。
3. `behavior contract`：定义 LLM 应该做什么、不应该做什么。
4. `output contract`：定义 Findings 结构与报告格式。
5. `review guidance`：定义何时可以下结论、何时必须标记人工复核。

模块边界如下：

- `skill entry`：向 Agent 说明这是一个“应用和数据安全密评标准 Skill”。
- `checklist sections`：按风险域组织检查点。
- `decision rules`：定义证据如何映射为风险结论。
- `guardrails`：约束 LLM 不得越界推断、不得伪造依据。
- `report template`：统一报告输出口径。

这个边界划分保证 Skill 始终只做“标准定义”，不会和具体执行器耦合。

## 6. 检测模型与规则体系

### 6.1 风险域

首版规则分为四个域：

- `crypto_at_rest`：静态数据保护，例如数据库字段、配置文件、日志、缓存中的敏感数据是否明文。
- `authentication_authorization`：认证、鉴权、会话、访问控制。
- `transport_security`：HTTPS/TLS、证书校验、双向认证、明文协议。
- `guomi_compliance_signals`：SM2/SM3/SM4、国密 TLS、算法替换情况。

### 6.2 规则类型

- 检查规则：定义应该关注哪些代码、配置、依赖、部署描述现象。
- 判定规则：定义“观察到什么证据时，可以得出什么风险结论”。
- 报告规则：定义每类问题必须输出哪些字段。
- 复核规则：定义哪些情形必须标记为人工复核。
- 例外规则：允许通过白名单、注释约定或配置文件抑制误报，但必须保留抑制记录。

### 6.3 LLM 判定约束

LLM 在使用此 Skill 时必须遵守以下约束：

- 只基于已读取的代码、配置、依赖和部署文件做结论。
- 不得引用未查看的文件，不得虚构实现细节。
- 不得把“缺少证据”等同于“没有问题”。
- 不得把“最佳实践偏差”直接表述为“密评不通过”，除非规则中已明确定义。
- 结论必须附带证据路径、位置和判断依据。
- 证据不足时必须输出 `manual_review` 而不是强行定性。

这样可以把模型角色限定为“按规则分析证据的审计员”，而不是自由发挥的代码助手。

### 6.4 结论分级

- `critical`：明确导致敏感数据泄露、身份绕过或明文传输。
- `high`：高概率安全缺陷或关键安全能力缺失。
- `medium`：存在较明显风险，但需要场景确认。
- `low`：最佳实践偏差或次要弱项。
- `manual_review`：证据不足，需人工判断。

### 6.5 置信度模型

每条 Finding 额外带 `confidence`：`high / medium / low`。

- `high`：存在明确 API、配置值或硬编码证据。
- `medium`：多条线索相互支撑，但缺少最终落点。
- `low`：仅命中启发式模式，不能直接下定论。

设计上把风险等级与置信度拆开，避免“高风险但低置信”被错误理解为已经坐实。

## 7. 数据结构与报告格式

### 7.1 Finding 统一模型

每个问题统一抽象为：

```text
Finding {
  id
  domain
  title
  severity
  confidence
  summary
  rationale
  evidence[]
  remediation
  status
}
```

其中 `evidence[]` 至少包含：文件路径、行号或片段、命中规则 ID、原始证据摘要。

`status` 取值建议为：`confirmed`、`suspected`、`manual_review`、`suppressed`。

### 7.2 Markdown 报告

Markdown 结构建议：

1. 报告摘要：扫描范围、时间、规则数量、问题计数。
2. 总体评估：按数据加密、鉴权、通信安全、国密适配四个域给出结论。
3. 高风险问题：优先展示 `critical/high`。
4. 详细问题清单：逐条列证据与建议。
5. 人工复核项：列出不够确定但值得审阅的问题。
6. 附录：扫描排除项、规则版本、抑制项。

### 7.3 HTML 报告

HTML 与 Markdown 内容保持一致，但增强：

- 顶部汇总卡片与风险分布。
- 域维度筛选。
- Finding 折叠展开。
- 证据片段高亮。

HTML 首版以单文件静态页面为目标，不引入前端构建链，保证 Skill 产物简单、可移植、易归档。

## 8. Skill 使用流程与质量要求

### 8.1 使用流程

Agent 使用该 Skill 时应遵循以下流程：

1. 读取目标仓库中与应用和数据安全相关的文件。
2. 按 Skill 定义的检查域逐项审阅。
3. 按 Skill 的判定规则形成 Findings。
4. 对证据不足项标记人工复核。
5. 按 Skill 定义的 Markdown/HTML 结构输出报告。

### 8.2 质量要求

- 报告中每个结论都必须可追溯到仓库证据。
- 高风险结论必须说明触发规则。
- 人工复核项必须说明为何不能直接定性。
- 报告必须明确本 Skill 不替代正式密评认证。

### 8.3 交付要求

- Skill 交付物应为文档和模板，而不是执行脚本。
- 至少应包含 `SKILL.md`、检查清单、输出模板和使用说明。
- 如果需要示例，使用示例提示词或示例报告，不实现模型调用代码。

### 8.4 分阶段落地

- Phase 1：完成 Skill 说明、范围定义、风险域检查标准。
- Phase 2：补充 LLM 行为约束、人工复核准则、输出模板。
- Phase 3：补充示例提示词、示例报告和例外规则说明。

这个分期与当前仓库状态匹配，能先把 Skill 做成清晰、可复用、可直接指导 Agent 的最小完整版本。

## 9. 决策摘要

- 目标：实现一个面向“应用和数据安全”的密评 Skill。
- 方法：采用“Skill 定义标准，宿主 Agent 按标准执行”的方案。
- 能力：聚焦数据加密、鉴权、通信安全与国密适配线索。
- 产物：同时输出 Markdown 与 HTML 报告。
- 约束：Skill 只定义标准与约束，不在 Skill 内实现扫描器或外部模型调用。
