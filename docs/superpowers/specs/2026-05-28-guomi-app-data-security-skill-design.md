# 密评 Skill 设计文档

## 1. 背景与目标

本设计面向 `agent-skills/` 新增一个聚焦“应用和数据安全”的密评 Skill。Skill 只覆盖代码与配置层面的静态分析，不扩展到基础设施、硬件密码模块、密钥生命周期平台或完整等保/密评流程编排。

目标是让 Agent 能基于代码仓库内容，识别并评估以下几类问题，并生成可交付的审计结论：

- 数据加密：敏感数据是否加密存储，是否存在明文密钥、弱算法或未加密落盘。
- 鉴权与访问控制：认证机制是否存在缺失、弱口令/硬编码凭据、越权风险、Token/Session 处理不当。
- 通信安全：传输层是否启用 TLS/HTTPS，是否存在明文协议、证书校验关闭、弱加密套件。
- 国密适配线索：是否使用 SM2/SM3/SM4、国密 TLS、国密证书链，或是否仍依赖非国密算法作为关键安全能力。

核心产出为两种格式：

- Markdown 报告：便于在仓库、PR、知识库中查看。
- HTML 报告：便于对外展示、归档与打印。

首版强调“能扫描、能判断、能解释原因、能给整改建议”，而不是追求全覆盖或形式化认证结论。

## 2. 范围

### 2.1 In Scope

- 扫描源码、配置文件、依赖清单、容器配置与常见部署描述文件。
- 基于规则和启发式证据判断应用与数据安全问题。
- 输出结构化问题清单、风险等级、证据位置、修复建议。
- 生成 Markdown 与 HTML 两种报告。
- 明确区分“已确认问题”“高置信线索”“需要人工复核”。

### 2.2 Out of Scope

- 动态渗透测试、运行时抓包、主动探测、联机攻击验证。
- 合规认证自动出证或替代人工密评。
- 覆盖主机、网络边界、数据库实例、密码机等基础设施层面。
- 自动修改业务代码或自动修复漏洞。

## 3. 设计原则

- 仓库直读，LLM 负责判定：系统优先把目标仓库中的源码、配置、依赖与部署文件直接提供给大模型，再由模型按照规则完成分析与归因。
- 规则显式化：每个安全域都要有可引用的检查规则、判定标准与输出模板，避免让模型自由发挥。
- 证据先于结论：每个结论都必须附带文件、位置、命中规则与判断依据。
- 保守输出：置信度不足时标记为“待人工确认”，避免伪确定性。
- 国密导向但不教条：既识别国密能力，也指出关键路径上不符合国密预期的传统算法使用。
- 上下文受控：虽然采用仓库直读，但仍需限制输入范围、分批读取策略和上下文窗口，避免成本失控与信息漂移。
- 可扩展：规则集、仓库读取策略、提示词模板、报告模板后续可独立扩展。

## 4. 候选方案与取舍

### 方案 A：纯规则扫描直接出结论

做法：使用 YAML/JSON 规则描述敏感模式、配置禁用项、算法黑白名单、鉴权/通信安全检查项，扫描代码与配置文件后直接生成 Findings。

优点：实现快、可解释性强、结果稳定、便于维护。

缺点：跨文件语义弱，对复杂业务封装、条件分支、组合式安全机制理解不足。

### 方案 B：纯 LLM 直接读仓库并给结论

做法：把源码和配置大段输入大模型，让模型自行判断应用和数据安全问题并生成报告。

优点：对上下文理解能力强，理论上覆盖面广。

缺点：成本高、上下文不可控、结果不稳定、证据链容易漂移，也难以保证按固定密评规则执行。

### 方案 C：证据收集管线 + LLM 按规则判定

做法：先通过文件发现、模式提取、配置解析、依赖分析等方式，把与安全相关的证据结构化收集出来；再将“规则 + 证据 + 输出格式要求”一起交给 LLM，让模型按规则完成分析、归因、分级和建议生成。

优点：兼顾大模型的语义理解能力与规则约束能力，既能提升复杂场景判断质量，又能保留稳定证据链和报告一致性。

缺点：需要设计好证据裁剪、提示词模板和输出校验，避免模型过度推断。

当前设计改为采用方案 B。实现重点不再是先构建复杂的证据收集管线，而是设计好“仓库读取策略 + 规则约束提示词 + 输出校验”，确保大模型直读代码仓库时仍能按固定密评口径输出稳定结论。

## 5. 系统架构

Skill 采用六段式流水线：

1. 输入解析层：接收目标仓库路径、可选语言/框架信息、扫描范围、排除目录。
2. 资产发现层：遍历源码、配置、依赖与部署文件，建立待分析文件索引。
3. 上下文构建层：按目录、文件类型和大小把仓库内容分批整理为适合 LLM 消费的上下文片段。
4. LLM 判定层：将规则、上下文片段和输出 schema 一并提交给大模型，由模型按规则完成分析、分级、归因与建议生成。
5. 结果校验层：校验模型输出格式、字段完整性、文件引用合法性，必要时进行重试或降级。
6. 报告输出层：渲染 Markdown 和 HTML 报告。

模块边界如下：

- `skill entry`：负责编排步骤、组织上下文、控制输出。
- `asset collector`：负责文件发现、类型识别、忽略规则。
- `context builder`：负责按窗口限制整理源码、配置和依赖上下文，决定分批输入策略。
- `prompt builder`：负责把规则、证据、输出约束组装成判定提示词。
- `llm adjudicator`：负责按规则生成 Findings。
- `result validator`：负责校验模型输出 schema、文件引用和分级合法性。
- `report renderer`：负责把结构化结果转换为 Markdown/HTML。

这个边界划分保证首版先把“仓库读取 + LLM 判定 + 结果校验”主链打通，后续即使补充更细的证据提取或 AST 能力，也不需要重写整个 Skill。

## 6. 检测模型与规则体系

### 6.1 风险域

首版规则分为四个域：

- `crypto_at_rest`：静态数据保护，例如数据库字段、配置文件、日志、缓存中的敏感数据是否明文。
- `authentication_authorization`：认证、鉴权、会话、访问控制。
- `transport_security`：HTTPS/TLS、证书校验、双向认证、明文协议。
- `guomi_compliance_signals`：SM2/SM3/SM4、国密 TLS、算法替换情况。

### 6.2 规则类型

- 仓库读取规则：定义哪些目录、文件类型和大小范围进入 LLM 上下文，避免无关文件污染判断。
- 配置解析规则：检查 Spring、Nginx、YAML、properties、Docker、K8s 配置中的安全选项，并将关键项直接带入模型上下文。
- 依赖识别规则：依据 `requirements.txt`、`pom.xml`、`go.mod`、`package.json` 推断安全库、国密库或弱库使用情况。
- 判定规则：把“什么代码或配置现象可以推导出什么风险”显式写入提示词或规则模板，由 LLM 严格参照执行。
- 例外规则：允许通过白名单、注释约定或配置文件抑制误报，但必须保留抑制记录。

### 6.3 LLM 判定约束

LLM 直接消费仓库内容，但输入过程必须受控：

- 安全域规则说明。
- 分批仓库上下文。
- 输出 schema。
- 风险等级与置信度定义。
- 禁止项，例如“不得引用未提供证据”“不得推断运行时事实”。

这样可以把模型角色限定为“按规则分析证据的审计员”，而不是自由发挥的代码助手。

### 6.4 结论分级

- `critical`：明确导致敏感数据泄露、身份绕过或明文传输。
- `high`：高概率安全缺陷或关键安全能力缺失。
- `medium`：存在较明显风险，但需要场景确认。
- `low`：最佳实践偏差或次要弱项。
- `manual_review`：证据不足，需人工判断。

### 6.5 置信度模型

每条 Finding 额外带 `confidence`：`high / medium / low`。

- `high`：存在明确 API、配置值或硬编码证据。
- `medium`：多条线索相互支撑，但缺少最终落点。
- `low`：仅命中启发式模式，不能直接下定论。

设计上把风险等级与置信度拆开，避免“高风险但低置信”被错误理解为已经坐实。

## 7. 数据结构与报告格式

### 7.1 Finding 统一模型

每个问题统一抽象为：

```text
Finding {
  id
  domain
  title
  severity
  confidence
  summary
  rationale
  evidence[]
  remediation
  status
}
```

其中 `evidence[]` 至少包含：文件路径、行号或片段、命中规则 ID、原始证据摘要。

`status` 取值建议为：`confirmed`、`suspected`、`manual_review`、`suppressed`。

### 7.2 Markdown 报告

Markdown 结构建议：

1. 报告摘要：扫描范围、时间、规则数量、问题计数。
2. 总体评估：按数据加密、鉴权、通信安全、国密适配四个域给出结论。
3. 高风险问题：优先展示 `critical/high`。
4. 详细问题清单：逐条列证据与建议。
5. 人工复核项：列出不够确定但值得审阅的问题。
6. 附录：扫描排除项、规则版本、抑制项。

### 7.3 HTML 报告

HTML 与 Markdown 内容保持一致，但增强：

- 顶部汇总卡片与风险分布。
- 域维度筛选。
- Finding 折叠展开。
- 证据片段高亮。

HTML 首版以单文件静态页面为目标，不引入前端构建链，保证 Skill 产物简单、可移植、易归档。

## 8. 执行流程、错误处理与测试策略

### 8.1 执行流程

Skill 的运行步骤：

1. 读取用户输入参数与目标路径。
2. 建立文件索引并识别可分析文件。
3. 按扫描策略分批读取仓库内容，并构造 LLM 上下文。
4. 将规则、上下文和输出约束发送给 LLM 做判定。
5. 校验并归并模型输出，生成统一 Findings。
6. 渲染 Markdown 与 HTML 报告。
7. 输出摘要结论与报告路径。

### 8.2 错误处理

- 路径不存在或无读取权限：立即失败并明确原因。
- 未识别语言/文件类型：继续扫描已识别部分，并在附录声明盲区。
- 仓库上下文过大：按目录或风险域分批判定，必要时裁剪低价值文件。
- LLM 输出不合规：触发格式修复重试；仍失败时降级为“仅证据摘要 + 待人工确认”。
- 报告渲染失败：至少保留结构化中间结果或 Markdown，避免完全无产出。

### 8.3 测试策略

- 单元测试：仓库分片、提示词构造、输出校验、误报抑制、Finding 归并、渲染器输出。
- 样例仓库测试：构造包含明文密钥、弱算法、缺失 TLS、未鉴权接口的最小示例仓库。
- 回归测试：针对固定仓库输入建立 golden reports，防止模型输出结构和判定口径漂移。
- 人工评审测试：抽样验证 `manual_review` 项是否具备足够上下文。

### 8.4 分阶段落地

- Phase 1：文件发现、仓库分片、LLM 判定主链、Markdown/HTML 报告、四大域基础规则。
- Phase 2：更细的上下文裁剪、Finding 归并、抑制机制、输出校验增强。
- Phase 3：补充轻量 AST 或证据提取能力，提升复杂场景判定准确率。

这个分期与当前仓库状态匹配，能先把 Skill 做成可演示、可迭代的最小完整版本。

## 9. 决策摘要

- 目标：实现一个面向“应用和数据安全”的密评 Skill。
- 方法：采用“LLM 直接读仓库 + 按规则判定”的方案。
- 能力：聚焦数据加密、鉴权、通信安全与国密适配线索。
- 产物：同时输出 Markdown 与 HTML 报告。
- 约束：只做静态分析与审计辅助，不替代正式密评认证。
