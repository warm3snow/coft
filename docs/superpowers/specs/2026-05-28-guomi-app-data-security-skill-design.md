# 密评 Skill 设计文档

## 1. 背景与目标

本设计面向 `agent-skills/` 新增一个聚焦“应用和数据安全”的密评 Skill。Skill 只覆盖代码与配置层面的静态分析，不扩展到基础设施、硬件密码模块、密钥生命周期平台或完整等保/密评流程编排。

目标是让 Agent 能基于代码仓库内容，识别并评估以下几类问题，并生成可交付的审计结论：

- 数据加密：敏感数据是否加密存储，是否存在明文密钥、弱算法或未加密落盘。
- 鉴权与访问控制：认证机制是否存在缺失、弱口令/硬编码凭据、越权风险、Token/Session 处理不当。
- 通信安全：传输层是否启用 TLS/HTTPS，是否存在明文协议、证书校验关闭、弱加密套件。
- 国密适配线索：是否使用 SM2/SM3/SM4、国密 TLS、国密证书链，或是否仍依赖非国密算法作为关键安全能力。

核心产出为两种格式：

- Markdown 报告：便于在仓库、PR、知识库中查看。
- HTML 报告：便于对外展示、归档与打印。

首版强调“能扫描、能判断、能解释原因、能给整改建议”，而不是追求全覆盖或形式化认证结论。

## 2. 范围

### 2.1 In Scope

- 扫描源码、配置文件、依赖清单、容器配置与常见部署描述文件。
- 基于规则和启发式证据判断应用与数据安全问题。
- 输出结构化问题清单、风险等级、证据位置、修复建议。
- 生成 Markdown 与 HTML 两种报告。
- 明确区分“已确认问题”“高置信线索”“需要人工复核”。

### 2.2 Out of Scope

- 动态渗透测试、运行时抓包、主动探测、联机攻击验证。
- 合规认证自动出证或替代人工密评。
- 覆盖主机、网络边界、数据库实例、密码机等基础设施层面。
- 自动修改业务代码或自动修复漏洞。

## 3. 设计原则

- 规则优先，启发增强：主路径采用可解释规则引擎，辅以模式识别与有限语义推断。
- 证据先于结论：每个结论都必须附带文件、位置、命中规则与判断依据。
- 保守输出：置信度不足时标记为“待人工确认”，避免伪确定性。
- 国密导向但不教条：既识别国密能力，也指出关键路径上不符合国密预期的传统算法使用。
- 可扩展：规则、报告模板、语言适配器后续可独立扩展。

## 4. 候选方案与取舍

### 方案 A：纯规则扫描

做法：使用 YAML/JSON 规则描述敏感模式、配置禁用项、算法黑白名单、鉴权/通信安全检查项，扫描代码与配置文件并直接出报告。

优点：实现快、可解释性强、结果稳定、便于维护。

缺点：跨文件语义弱，容易漏掉间接调用和复杂封装场景。

### 方案 B：AST/语义分析优先

做法：按语言构建 AST 分析器，对调用链、注解、中间件配置、加解密 API 和认证流程做更深层建模。

优点：准确率与上下文理解更强。

缺点：实现成本高，语言扩展慢，不适合作为当前仓库里第一个 Skill 的落地路径。

### 方案 C：主规则引擎 + 辅助语义/模式增强

做法：主路径采用规则扫描，针对高价值场景补充轻量 AST 或上下文聚合能力，例如配置与代码联合判断、框架约定识别、同一风险跨文件归并。

优点：在可落地性、可解释性、扩展性之间平衡最好。

缺点：设计上需要明确“规则结论”和“推断结论”的边界，避免结果混淆。

推荐采用方案 C，并以方案 A 的实现骨架起步，预留 B 类能力的插槽。这与已确认的“主 1，辅 2+3”方向一致。

## 5. 系统架构

Skill 采用五段式流水线：

1. 输入解析层：接收目标仓库路径、可选语言/框架信息、扫描范围、排除目录。
2. 资产发现层：遍历源码、配置、依赖与部署文件，建立待分析文件索引。
3. 分析引擎层：执行规则匹配、配置关联、轻量语义增强与风险聚合。
4. 结果建模层：把命中结果统一为结构化 Finding，补充风险等级、置信度、证据与整改建议。
5. 报告输出层：渲染 Markdown 和 HTML 报告。

模块边界如下：

- `skill entry`：负责编排步骤、组织上下文、控制输出。
- `asset collector`：负责文件发现、类型识别、忽略规则。
- `rule engine`：负责执行单文件或多文件规则。
- `evidence correlator`：负责将多个线索归并为单个风险结论。
- `report renderer`：负责把结构化结果转换为 Markdown/HTML。

这个边界划分保证首版可先做规则与报告，后续再增强关联分析而不需要重写整个 Skill。

## 6. 检测模型与规则体系

### 6.1 风险域

首版规则分为四个域：

- `crypto_at_rest`：静态数据保护，例如数据库字段、配置文件、日志、缓存中的敏感数据是否明文。
- `authentication_authorization`：认证、鉴权、会话、访问控制。
- `transport_security`：HTTPS/TLS、证书校验、双向认证、明文协议。
- `guomi_compliance_signals`：SM2/SM3/SM4、国密 TLS、算法替换情况。

### 6.2 规则类型

- 关键字/正则规则：发现硬编码密码、AK/SK、私钥片段、`verify=false`、`md5`、`des`、`http://` 等。
- 配置规则：检查 Spring、Nginx、YAML、properties、Docker、K8s 配置中的安全选项。
- 依赖规则：依据 `requirements.txt`、`pom.xml`、`go.mod`、`package.json` 推断安全库或弱库使用情况。
- 关联规则：把“接口暴露 + 缺少鉴权注解”“TLS 关闭 + 明文回源配置”等组合成更强结论。
- 例外规则：允许通过白名单、注释约定或配置文件抑制误报，但必须保留抑制记录。

### 6.3 结论分级

- `critical`：明确导致敏感数据泄露、身份绕过或明文传输。
- `high`：高概率安全缺陷或关键安全能力缺失。
- `medium`：存在较明显风险，但需要场景确认。
- `low`：最佳实践偏差或次要弱项。
- `manual_review`：证据不足，需人工判断。

### 6.4 置信度模型

每条 Finding 额外带 `confidence`：`high / medium / low`。

- `high`：存在明确 API、配置值或硬编码证据。
- `medium`：多条线索相互支撑，但缺少最终落点。
- `low`：仅命中启发式模式，不能直接下定论。

设计上把风险等级与置信度拆开，避免“高风险但低置信”被错误理解为已经坐实。

## 7. 数据结构与报告格式

### 7.1 Finding 统一模型

每个问题统一抽象为：

```text
Finding {
  id
  domain
  title
  severity
  confidence
  summary
  rationale
  evidence[]
  remediation
  status
}
```

其中 `evidence[]` 至少包含：文件路径、行号或片段、命中规则 ID、原始证据摘要。

`status` 取值建议为：`confirmed`、`suspected`、`manual_review`、`suppressed`。

### 7.2 Markdown 报告

Markdown 结构建议：

1. 报告摘要：扫描范围、时间、规则数量、问题计数。
2. 总体评估：按数据加密、鉴权、通信安全、国密适配四个域给出结论。
3. 高风险问题：优先展示 `critical/high`。
4. 详细问题清单：逐条列证据与建议。
5. 人工复核项：列出不够确定但值得审阅的问题。
6. 附录：扫描排除项、规则版本、抑制项。

### 7.3 HTML 报告

HTML 与 Markdown 内容保持一致，但增强：

- 顶部汇总卡片与风险分布。
- 域维度筛选。
- Finding 折叠展开。
- 证据片段高亮。

HTML 首版以单文件静态页面为目标，不引入前端构建链，保证 Skill 产物简单、可移植、易归档。

## 8. 执行流程、错误处理与测试策略

### 8.1 执行流程

Skill 的运行步骤：

1. 读取用户输入参数与目标路径。
2. 建立文件索引并识别可分析文件。
3. 执行规则扫描与关联分析。
4. 归并重复问题，生成统一 Findings。
5. 渲染 Markdown 与 HTML 报告。
6. 输出摘要结论与报告路径。

### 8.2 错误处理

- 路径不存在或无读取权限：立即失败并明确原因。
- 未识别语言/文件类型：继续扫描已识别部分，并在附录声明盲区。
- 规则执行异常：记录错误规则，不中断整体报告生成。
- 报告渲染失败：至少保留结构化中间结果或 Markdown，避免完全无产出。

### 8.3 测试策略

- 单元测试：规则命中、误报抑制、Finding 归并、渲染器输出。
- 样例仓库测试：构造包含明文密钥、弱算法、缺失 TLS、未鉴权接口的最小示例仓库。
- 回归测试：针对已知规则集建立 golden reports，防止输出结构漂移。
- 人工评审测试：抽样验证 `manual_review` 项是否具备足够上下文。

### 8.4 分阶段落地

- Phase 1：规则框架、文件发现、Markdown/HTML 报告、四大域的基础规则。
- Phase 2：配置与代码联合判断、Finding 归并、抑制机制。
- Phase 3：轻量 AST/框架适配，提升鉴权与加密场景识别准确率。

这个分期与当前仓库状态匹配，能先把 Skill 做成可演示、可迭代的最小完整版本。

## 9. 决策摘要

- 目标：实现一个面向“应用和数据安全”的密评 Skill。
- 方法：采用“规则优先 + 轻量语义增强”的混合方案。
- 能力：聚焦数据加密、鉴权、通信安全与国密适配线索。
- 产物：同时输出 Markdown 与 HTML 报告。
- 约束：只做静态分析与审计辅助，不替代正式密评认证。
