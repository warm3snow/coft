# 密评标准

## 1. 总体要求

审阅时只基于已查看的仓库内容做结论。

每个结论都必须附带：

- 文件路径
- 行号或片段位置
- 触发的检查点
- 判断理由

如果证据不足，必须标记为 `manual_review`。

## 2. 审阅顺序

1. 先看配置、依赖、部署描述，再看业务代码。
2. 先识别明确风险，再处理最佳实践偏差。
3. 先写证据，再写结论。
4. 不能确认时，转入 `manual_review`。

## 3. 风险等级

- `critical`：明确导致敏感数据泄露、身份绕过或明文传输。
- `high`：高概率安全缺陷或关键安全能力缺失。
- `medium`：存在较明显风险，但需要业务场景确认。
- `low`：次要弱项或最佳实践偏差。
- `manual_review`：证据不足，必须人工确认。

## 4. 通用判定规则

- 看到明确明文凭据、私钥、弱鉴权、关闭证书校验等强证据时，可以直接定性。
- 只看到字符串、常量、注释或局部代码，不能确认真实用途时，优先 `manual_review`。
- 最佳实践偏差可以记为 `low` 或 `medium`，但不能直接写成“密评不通过”。
- 同一问题在多个文件重复出现时，合并为一个 Finding，证据列出多个位置。
- 不能把“未观察到”写成“确定不存在”或“已满足”。

## 5. 风险域

### 3.1 数据加密

检查对象：

- 敏感字段处理逻辑
- 配置文件中的密钥、证书、凭据
- 日志、缓存、落盘文件
- 加解密算法调用

检查点：

- 是否存在明文密钥、私钥、密码、AK/SK。
- 是否使用弱算法或不安全模式。
- 是否把敏感数据明文写入日志、缓存或本地文件。
- 是否存在应加密而未加密的持久化线索。

结论规则：

- 明确的明文密钥或私钥片段通常至少为 `high`。
- 明确的弱算法用于敏感数据保护时，通常至少为 `medium`，严重场景可上调。
- 仅出现算法名称但无使用上下文时，应保守处理，可标记 `manual_review`。

### 3.2 鉴权与访问控制

检查对象：

- 登录、认证、授权逻辑
- 会话、Token、Cookie 处理
- 路由保护、中间件、注解
- 默认账号、硬编码凭据

检查点：

- 是否存在未鉴权接口或鉴权绕过线索。
- 是否存在硬编码用户名、密码、Token。
- 是否存在弱口令、默认口令或调试后门。
- 是否缺少权限校验、角色校验或资源级访问控制。

结论规则：

- 明确暴露敏感接口且无鉴权保护时，通常为 `high` 或 `critical`。
- 仅看到接口定义但看不到路由保护全貌时，应考虑 `manual_review`。

### 3.3 通信安全

检查对象：

- HTTP/TLS 配置
- 证书校验逻辑
- 明文协议使用
- 服务间通信配置

检查点：

- 是否使用明文 `http://`、FTP、Telnet 等不安全协议。
- 是否关闭证书校验或跳过主机名校验。
- 是否存在弱 TLS 配置或调试性跳过校验代码。

结论规则：

- 明确关闭证书校验通常至少为 `high`。
- 明文回源、明文敏感传输可提升为 `critical`。
- 仅出现字符串常量而无实际使用上下文时，避免直接下结论。

### 3.4 国密适配线索

检查对象：

- SM2/SM3/SM4 使用情况
- 国密 TLS 或国密证书链线索
- 关键安全路径上的算法选择

检查点：

- 是否存在国密算法使用线索。
- 是否在关键路径仍依赖非国密算法。
- 是否能从配置和依赖中观察到国密适配能力缺失。

结论规则：

- 该域更多用于“适配线索”判断，不宜在证据薄弱时直接给出强结论。
- 如果只是未观察到国密实现，通常应使用 `manual_review` 或保守结论。

## 6. 人工复核规则

以下情况优先标记 `manual_review`：

- 只能看到局部代码，看不到完整调用链。
- 只能看到配置片段，看不到实际部署生效情况。
- 无法确认敏感数据是否真实落盘或真实传输。
- 只能看到接口定义，看不到统一鉴权中间件或网关规则。

## 7. 例外规则

允许合理抑制误报，但必须在报告中说明：

- 为什么抑制
- 抑制基于什么证据
- 抑制是否需要人工复核

## 8. 禁止写法

- 不要写“未发现任何问题”，除非已明确说明审阅范围。
- 不要写“系统安全”这类没有证据支撑的总结。
- 不要把“看不到实现”写成“实现缺失”。
- 不要把适配线索不足直接写成合规失败。
