# 文档标准

## 1. 目标

这套文档的目标，是让 AI 在进入仓库后能够快速建立五个认知：

- 系统如何组成
- 系统暴露和依赖哪些接口
- 数据如何存储和演进
- 服务如何运行和部署
- 应该按什么顺序阅读这些文档

这套 Skill 只定义标准，不实现执行器。

## 2. 证据模型

所有文档内容按以下三类管理：

### 2.1 observed

直接来自以下证据：

- 仓库目录结构
- 源码与测试
- OpenAPI、proto、GraphQL schema、IDL
- ORM 模型、SQL、迁移、seed
- Dockerfile、Compose、Kubernetes、Helm、Terraform、CI/CD 脚本
- README、配置文件、环境变量模板、运维脚本

这类信息可以直接写入文档。

### 2.2 inferred

由多个证据保守推导而来，例如：

- 某服务很可能依赖某数据库
- 某模块大概率是领域核心
- 某发布步骤大概率由 CI 工作流触发

这类信息只能保守表达，不能写成硬事实。

### 2.3 open_question

无法从仓库静态内容确认，但会影响 AI coding 决策的信息，例如：

- 实际线上拓扑
- 某接口是否仍对外开放
- 某表是否已废弃但仍保留
- 发布顺序与回滚策略是否存在人工流程

这类信息必须进入 `open-questions`。

## 3. 默认文档集

默认生成以下文件：

1. `AGENTS.md`
2. `docs/ai/architecture.md`
3. `docs/ai/api.md`
4. `docs/ai/database.md`
5. `docs/ai/deployment.md`

存在未确认事项时，再创建：

6. `docs/ai/open-questions.md`

规则：

- 四类核心文档优先承载事实。
- `AGENTS.md` 默认生成，但只做短索引。
- 小仓库允许合并四类文档，但不建议省略 `AGENTS.md`。

## 4. AGENTS.md 规范

`AGENTS.md` 必须符合以下要求：

- 默认生成。
- 文字尽量少，建议控制在一到两屏内。
- 只包含阅读顺序、文档索引、少量硬规则。
- 不重复架构、接口、数据库、部署文档正文。
- 不写未经确认的流程、拓扑或负责人信息。

至少包含：

1. `Start Here` 或等价阅读顺序
2. 四类文档索引
3. `open-questions` 入口
4. 2 到 4 条核心规则

## 5. 架构文档规则

架构文档的目标，是让 AI 知道系统怎么分层、怎么协作、哪里是主要入口。

必须包含：

- 顶层目录和主要模块
- 服务或应用边界
- 关键入口文件、启动入口、主流程
- 模块依赖关系或调用关系
- 外部依赖或第三方集成线索
- 高风险共享模块

禁止写法：

- 只给目录树，不解释关系
- 根据命名直接脑补分层设计
- 编造“标准 DDD 架构”“微服务架构”等标签

## 6. 接口文档规则

接口文档的目标，是让 AI 知道系统对内对外的交互契约。

必须覆盖能观察到的接口类型，例如：

- HTTP API
- RPC/gRPC
- GraphQL
- WebSocket
- 消息队列或事件
- 第三方回调或 SDK 接入点

每类接口尽量包含：

- 路径或方法名
- 协议类型
- 请求结构来源
- 响应结构来源
- 鉴权或访问控制线索
- 所属实现文件
- 上下游依赖

禁止写法：

- 只写接口路径，不写语义和实现位置
- 仅根据前端调用字符串推测后端真实契约
- 把没看到的字段写进文档

## 7. 数据库文档规则

数据库文档的目标，是让 AI 知道系统的数据边界和演进方式。

必须包含：

- 数据存储类型和实例线索
- 主要表、集合或模型
- 关键字段、索引、关联关系线索
- 迁移机制或 schema 演进入口
- 数据访问层位置
- 高风险数据变更边界

禁止写法：

- 只写“使用 MySQL/PostgreSQL”
- 把业务猜测写成表关系事实
- 没看到迁移却写“数据库自动同步 schema”

## 8. 部署文档规则

部署文档的目标，是让 AI 知道代码如何成为运行中的系统。

必须包含：

- 可观察到的部署单元，例如 api、worker、cron、frontend
- 构建与镜像线索
- 运行时配置来源
- 编排方式，例如 Docker Compose、Kubernetes、Helm、systemd、serverless
- CI/CD 或发布脚本线索
- 健康检查、依赖服务、启动顺序线索

禁止写法：

- 只写“支持容器化部署”
- 未看到发布流程却写“自动发布到生产”
- 把推测的拓扑写成线上事实

## 9. open-questions 规则

以下情况优先进入 `open-questions`：

- 代码里能看到调用，但看不到被调服务定义
- 能看到模型使用，但看不到完整表结构
- 能看到部署清单，但看不到真实环境差异
- 能看到接口实现，但看不到鉴权全链路
- 能看到 CI，但无法确认是否就是正式发布入口

每个问题至少包含：

- 问题本身
- 当前无法确认的原因
- 建议确认方式
- AI 在未确认前的保守行为

## 10. 约束提炼规则

文档必须提炼出对 AI coding 有实际约束价值的结论，例如：

- 修改某 handler 前必须同步检查对应 DTO 和接口测试
- 修改某表结构前必须同步检查迁移和 seed
- 修改共享配置前必须确认哪些部署单元会受影响
- 修改消息结构前必须检查生产者和消费者两侧

不要写空泛结论，例如：

- 注意系统影响
- 谨慎修改数据库
- 确保部署稳定

## 11. 禁止写法

- 不要把 README 概述当成架构文档。
- 不要把 swagger 页面标题当成完整接口文档。
- 不要把 ORM 类名列表当成数据库文档。
- 不要把 Dockerfile 单独存在当成完整部署流程。
- 不要引用未查看的文件或目录。
- 不要把猜测写成“系统采用……架构”。
